# SDK reference demo release

This release makes the reference demo reproducible from the repository: original
reference-frame geometry, the SDK renderer and a pinned MediaPipe runtime.

**Recorded release status (2026-11-21):** [PR #4](https://github.com/franksunye/visutry-tryon-sdk/pull/4)
records a published same-origin demo at <https://visutry-sdk-demo.vercel.app> for
tested/deployed commit `a07a0097ca616f2c391f08237ec917c16fb28a99`, subsequently
merged into `main` as `b8e3b1ae`. The record includes anonymous HTTPS asset checks
and browser-fixture evidence. These are recorded release results, not a fresh
availability check performed for this documentation update.

The dedicated R2 asset origin remains follow-up work. Its pending publication
does not invalidate the released same-origin reference. Real-device acceptance
and npm package publication are separate and are not established by this release.

## Scope and evidence limits

- `reference-frame-v1` is original VisuTry demonstration geometry, generated by `scripts/generate-reference-glasses.mjs` and marked `demoOnly: true`. Its dimensions are design parameters, not measurements of a physical product. See [asset provenance](../packages/demo-assets/reference/v1/PROVENANCE.md).
- The demo uses the actual GLB loader, renderer and MediaPipe Face Landmarker. Its JavaScript, WASM and model are served from the demo origin; reference geometry is also available from that origin for a reproducible baseline.
- The five legacy entries under `cdn.visutry.com/demo/glasses/` are separate assets. TLS failures and diagnostic HTTP 404s do not establish whether those files ever existed. This release does not recover or validate those five styles.
- Browser automation uses a public-domain NASA still photograph converted into a synthetic camera video and supplied through Chromium's fake camera. It exercises the real detector and renderer for that fixed fixture. It does not establish physical fit, optical accuracy, a moving live-camera experience, mobile performance, WeChat compatibility or real-device acceptance.
- This workflow does not publish npm packages. Existing package-release automation is separate.

## Reproduce the release gates

Run from the repository root using Node.js 22 and pnpm 10.31.0:

```bash
pnpm install --frozen-lockfile
pnpm demo:prepare
pnpm lint
pnpm typecheck
pnpm test
pnpm demo:build
pnpm --filter visutry-web-demo exec playwright install --with-deps chromium
```

`demo:prepare` checks committed geometry without regenerating it and prepares the pinned MediaPipe files. `demo:build` includes runtime preparation, builds the SDK packages and writes the static demo to `examples/web-demo/dist`.

Install `ffmpeg` if needed, then prepare an absolute fake-camera path and run the selected reference suite:

```bash
ffmpeg -hide_banner -loglevel error -y \
  -loop 1 -i examples/web-demo/e2e/fixtures/astronaut.png \
  -vf 'crop=320:320:60:0,scale=480:480,pad=640:480:80:0' \
  -r 15 -t 2 -pix_fmt yuv420p /tmp/visutry-reference.y4m
VISUTRY_FAKE_VIDEO=/tmp/visutry-reference.y4m pnpm demo:test
```

The selected file is `examples/web-demo/e2e/reference-demo.spec.ts`. Playwright starts the local demo server and supplies the fake-camera input; it must not replace the renderer or landmark detector with mocks. The older `demo.spec.ts` is outside this recovery gate and is not evidence of coverage here.

For a local environment that requires an existing Chromium executable, `PLAYWRIGHT_EXECUTABLE_PATH` can point to that executable. CI must leave it unset and use the browser installed by Playwright. See [.github/workflows/demo-reference.yml](../.github/workflows/demo-reference.yml) for the PR and main-branch gates. A passing local run is not a recorded GitHub Actions run or production test.

## Dedicated R2 asset publication

The intended asset origin is `https://sdk-assets.visutry.com`, using a dedicated
R2 bucket and custom domain. PR #4 records bucket creation, with object uploads,
CORS and custom-domain activation still pending. The intended hostname must not
be presented as a verified working asset URL. The checked-in and published
same-origin reference remains the baseline until remote publication passes all
checks. R2 is an optional distribution follow-up to the completed same-origin
release, not a requirement to reproduce that release.

1. Upload only the verified reference release files under a versioned key such as `/reference/v1/reference-frame-v1.glb`, with their provenance and license. Compare the uploaded bytes with the committed SHA-256. Do not overwrite a released immutable key; publish a new version to change content.
2. Wait until the R2 custom domain and certificate are active. Test with normal HTTPS certificate validation. An insecure `curl -k` result is diagnostic only.
3. For a public, credential-free model, allow `GET` and `HEAD` from the demo origin, or `*` if the asset is intentionally public to all origins. Test with an `Origin` request header; a response without that request header is not CORS evidence. Configure range-related headers only if the client uses them.
4. Serve GLB as `model/gltf-binary`. Give immutable versioned files `Cache-Control: public, max-age=31536000, immutable`. Keep mutable manifests short-lived. Cloudflare's default cached-extension list does not include `.glb`; add a cache rule scoped to this asset hostname and versioned path if edge caching is required.
5. After changing CORS on cached content, purge affected keys and repeat the browser check. Confirm the real renderer loads the remote URL from the public demo origin before changing any default manifest.

References: Cloudflare [R2 public buckets and custom domains](https://developers.cloudflare.com/r2/buckets/public-buckets/), [CORS](https://developers.cloudflare.com/r2/buckets/cors/) and [default cache behavior](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/).
